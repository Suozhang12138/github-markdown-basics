# T04 · 增强雷达图：可视化设计实现

> 对应考核题目 **1.4【前端方向必做】可视化设计实现**。

用普通雷达图展示 5 个岗位报名人数的**平均值**，同时在每个指标扇区内，用**地平线图**展示该指标全部数据点的**分布**。

## 一、交付物与运行方式

| 路径 | 内容 |
| --- | --- |
| `src/` | 源代码（纯函数层 + 渲染层 + 构建脚本 + 数据） |
| `build/index.html` | **编译产物，双击即可在浏览器打开**，无需任何本地服务器 |
| `preview.png` | 渲染结果预览（由当前数据集生成） |
| `preview.provenance.json` | 预览图的来源锚点：记录它由哪一份产物（SHA-256）渲染而来，防止图文不符 |

```bash
cd T04
node src/build.mjs                                  # 构建 + 数值/产物自检
node src/reverse-verify.mjs                         # 反向验证：防护拆掉后必须变红
node src/check-render.mjs --allow-no-browser        # 渲染自检：真跑产物脚本并核对 SVG
node src/check-render.mjs --update-preview          # 重出预览图（需浏览器可用，见第七节）
```

`build.mjs` 会先在 Node 里跑一遍数值校验（9 项断言），再对产物做 15 项自检，全部通过才写出文件；任一项不过就中止并返回非 0 退出码。本项目**零依赖**——三个脚本只用 Node 内置模块，不需要 `npm install`。

## 二、图表设计思路

### 2.1 拆解题目要求

题目给了三张参考子图，实际上是在描述一个**分层的复合图表**：

- **子图 1**：雷达图的一个扇区，并标出地平线图的 X 轴（红）与 Y 轴（绿）
- **子图 2**：一个普通的地平线图，展示该维度的全部数值分布
- **子图 3**：把子图 2 放进子图 1 的扇区里，得到最终效果

所以核心问题是：**地平线图的两个轴，分别对应扇区的哪个方向？**

### 2.2 关键决策：半径给"数值"，角度给"密度"

我的选择是：

- **半径方向 = 数值轴**（与雷达图共用同一套刻度，`0 → valueMax` 线性映射到 `R0 → RM`）
- **角度方向 = 密度轴**（以扇区角平分线为中心，密度越大向两侧张开越多）

这样做而不是反过来，理由有三条：

1. **让两张图真正叠合，而不是并排。** 雷达图里"半径 = 数值"是它的固有语义。如果改成"角度 = 数值"，那么平均值就落在某个角度上，而雷达图的多边形顶点定义在半径上 —— 两者会各说各话。反过来，让地平线图的数值轴也用半径，平均值多边形和分布曲线就落在**同一条轴**上，可以直接对齐着读。这是这张图能不能"叠加"成立的关键。
2. **扇区形状恰好合适。** 扇区在半径方向上是连续的（从圆心到外缘），天然适合当一条一维的数值轴；而在角度方向上宽度有限，正适合承载"向两侧张开的密度"。
3. **密度需要对称。** 地平线图的高度是单侧的（从基线向上），直接塞进扇区会只占半边、浪费另一半。把密度以角平分线为轴左右对称铺开，整个扇区都被利用，而且"中间厚、两头薄"的形状本身就传达了分布信息。

红色 X 轴画在角平分线上（径向），绿色 Y 轴画在该维度数值起点的切向基线上，两者垂直 —— 与子图 1 的标注一致。

### 2.3 地平线图的原理

地平线图（Horizon Chart）是把面积图在**垂直方向折叠**以压缩占位的技术：

1. 把数值域等分成 `bands` 段；
2. 第 `b` 层只保留"超过 `b/bands` 的那部分"，即 `clamp(v − b/bands, 0, 1/bands) × bands`；
3. 每层都从同一条基线起画，用**递进加深的颜色**叠加。

结果是：图形高度被压缩到 `1/bands`，但"哪里更密"仍然由颜色深浅编码。本项目用 3 层，所以每层厚度归一化到 `[0,1]` 后，只派生出"张开多少角度"这一个几何量。

实现里有一条不变量：**第 b 层处处不超过第 b−1 层**（层与层是嵌套的）。构建脚本会断言这一点，避免折叠算错却看不出来。

### 2.4 密度怎么来的

地平线图需要一条连续的"剖面"，而不是一堆离散点。这里用**高斯核密度估计（KDE）**，带宽取 Silverman 经验规则：

```
h = 0.9 · min(σ, IQR/1.34) · n^(−1/5)
```

取 `σ` 与 `IQR/1.34` 的较小值，是为了在双峰或长尾数据上不过度平滑（这正是本题 Data Scientist 那一维的情况）。相比直方图，KDE 只需要一个可以完全由数据推导出的参数，不需要手调柱子数量。

在每个维度的 `[min, max]` 两侧各留 `1.2h` 余量后，均匀取 73 个采样点，得到密度剖面。

## 三、这套图能看出什么（雷达图看不出来的东西）

| 岗位 | 均值 | 中位数 | 分布形状（从地平线图读出） |
| --- | --- | --- | --- |
| Software Engineer | 131.4 | 119.5 | 单峰、右偏，量级最大 |
| Product Manager | 72.2 | 70.0 | 近似正态，最"规矩"的一维 |
| HR Specialist | 30.2 | 27.5 | 单峰、右偏，量级最小 |
| Data Scientist | 81.1 | **99.0** | **明显双峰：一批企业招 40 人左右，另一批招 110 人以上** |
| Marketing Coordinator | 53.7 | 50.0 | 较平坦，接近均匀 |

**最有价值的一条**：Data Scientist 的均值（81.1）明显低于中位数（99.0），光看雷达图只会得到一个数；而地平线图上那个明显的"凹口"直接暴露了双峰结构 —— 说明市场上这类岗位存在两种截然不同的招聘规模。这正是"增强"雷达图相对于普通雷达图的增益所在。

（以上统计基于当前占位数据集，替换官方数据后结论会随之变化。）

## 五、几个工程决策

**1. 为什么产物要把数据内联，而不是让 html 去 `fetch` CSV？**

题目要求"确保可直接浏览"。用 `file://` 双击打开时，`fetch` 本地文件会被 CORS 拦截，`<script type="module">` 也会因跨源限制加载失败。所以构建时把 CSS、JS、CSV 全部内联，并用**普通（非 module）脚本**执行 —— 双击即看，不依赖任何本地服务器。`src/index.html` 保留了模块化的开发态，但它需要 `http` 环境。

这里有一条容易被混为一谈的地方：**「产物能不能移植」和「源码能不能构建」是两件事**，前者要按"零外部依赖 + 不依赖特定协议特性"来验收。因此构建脚本里加了对应断言：产物中 `type="module"` / `crossorigin` 计数为 0、根绝对路径引用为 0、外部资源 URL 为 0。

**2. 为什么刻度取整用更密的梯级？**

最初用常见的 `{1, 2, 5, 10}` 梯级，最大值 278 会被归到 500 —— 近一半半径被浪费，均值多边形被压在内圈、分布也被摊薄。改用 `{1, 1.2, 1.5, 2, 2.5, 3, 4, 5, 6, 8, 10}` 后归到 300，图面利用率明显改善。

**3. 轴标记为什么要单独放在最上层？**

地平线图的密度是以角平分线为轴对称铺开的，也就是说**角平分线一定被密度图盖住**。红轴恰好画在角平分线上，如果按常规顺序图层放在中间，它会整条消失。这是实际渲染出来、发现问题后才调整的（第一版就是全被盖住）。

**4. 分带为什么要"分两层"夹住均值多边形？**

地平线图的颜色深浅本身就是它的信息载体。如果均值多边形整个盖在它上面（第一版就是这样），多边形内部那一片分布就被紫色填充糊掉了，五个扇区的分带几乎看不见。现在的顺序是：

```
扇区底 → 网格 → 浅层分带 → 均值多边形 → 网格(淡) → 深层分带(multiply) → 轴标记 → 刻度 → 标签
```

最浅的一层压在下面、深的两层用 `mix-blend-mode: multiply` 叠在上面，于是均值多边形的轮廓仍然连续可读，而分布最深的部分不会被填充吃掉。`check-render.mjs` 会断言这个先后顺序（比对 SVG 里 `layer-density` / `layer-radar` / `layer-density-over` 的偏移量）。

**5. 为什么刻度标签要写 `stroke` 而不是只写 `paint-order`？**

SVG 文本默认没有描边，只写 `paint-order: stroke fill` 不会凭空产生一层白边——必须同时给出 `stroke` 颜色和 `stroke-width`，白边才会真的画出来。修正前 300 那个刻度正好压在扇区分隔线上，是花掉的。

**6. 三种视图切换**

工具栏的「仅雷达图 / 仅分布 / 结合视图」直接对应题目图解的**子图 1 / 子图 2 / 子图 3**，方便对照检验两个图层各自的正确性。

> 这里踩过一个坑：`app.js` 末尾的自动启动写成 `if (typeof document !== 'undefined') boot();`。模块态下没问题，但构建把它内联成普通脚本后 `document` 也存在，会启动一次；构建脚本末尾为防"脚本被剥离"又显式调了一次 `boot()` —— 结果 `boot()` 跑两遍，三个视图按钮各绑两组监听器。现在由构建侧在窗口上立 `__T04_INLINE__` 标记来跳过自动启动，`check-render.mjs` 会断言每个按钮的 handler 数量恰好为 1。

## 六、怎么证明这些东西是对的

三份脚本，各管一段，都能单独跑：

| 脚本 | 管什么 | 当前结果 |
| --- | --- | --- |
| `build.mjs` | 算法数值 + 产物结构/可移植性 | 数值断言 9 项 + 产物自检 15 项，全过 |
| `reverse-verify.mjs` | 证明上面的防护**不是假绿** | 13 项防护拆掉后全部变红 |
| `check-render.mjs` | 真跑产物脚本，核对它画出来的 SVG | 断言 30 项全过（含几何误差 0.004px） |

其中三点值得说明：

- **反向验证**：一个永远为 `true` 的断言和没有断言是一样的。`reverse-verify.mjs` 拿产物，把每条约束逐个"拆掉"（注入 `<script type="module">`、绝对路径、外链、把 `function boot` 改名……），再跑**同一份规则**，确认对应那一条真的变红。规则与破坏手法放在 `artifact-checks.mjs` 里，两个脚本共用，避免"两边各写一份正则、其中一份没覆盖"的假绿。
  这套做法第一次跑就抓出了自检自身的三个缺陷：① 内联脚本字符串只算了一次就复用，破坏只作用在 html 上、读该字符串的规则永远看到旧内容；② `/^\s*(export|import)\s/m` 只覆盖行首，`var x; export {x};` 这种漏网；③ 用 `\bboot\b` 之类子串判断符号是否存在，结果注释里一句"显式调 boot()"就能让它恒为 true。
- **渲染自检**：产物里的 `<svg id="chart">` 在源 HTML 里是**空的**，图形全部由内联脚本在运行时写入。所以静态解析只能看到一个空壳（第一版自检就是这么写的，14 项断言全红，问题出在测错了对象）。现在改成：给内联脚本一个极小 DOM 桩，在 Node 里**把它真跑一遍**，再对它生成的 SVG 做几何断言 —— 包括用模型反推每个均值顶点应有的半径，误差 0.004px。
- **预览图的可追溯性**：`preview.provenance.json` 记录这张 `preview.png` 是从哪一份 `build/index.html` 渲染来的（SHA-256）。构建是**确定性**的（同样的输入产出逐字节相同的产物），所以用内容哈希做锚点，而不是 mtime —— 重跑一次构建会刷新 mtime 但内容没变，按 mtime 判"过期"是假警报。产物内容一变哈希就对不上，`check-render.mjs` 当场报红（已用篡改哈希的方式反向验证过会失败）。

## 七、渲染验证的环境限制

`check-render.mjs` 还有一层"隔离副本 + 无头浏览器"验证：把 `build/` 单独复制到一个不带工程、不带 `node_modules` 的目录，再用 Edge 无头模式打开，断言执行完 JS 之后的 DOM，并重出 `preview.png`。

这一层在开发用的这台机器上**不稳定，多数时候失败**：

- 当前进程以管理员权限（elevated）运行，Chromium 系浏览器在这种情况下**有时**拒绝渲染 —— `--screenshot` / `--dump-dom` 不产出任何输出（`--dump-dom` 退出码 21），但同样以管理员权限运行的 shell 里**偶尔又能成功**（当前 `preview.png` 就是这样出图的）；
- 尝试过的组合均无法稳定复现：`--no-sandbox`、`--headless=old`、`--single-process`、`--in-process-gpu`、最小 `data:` URL、换 `--user-data-dir` 到 `%TEMP%`、换输出目录、Node `spawnSync` 各种 `stdio`/`windowsHide` 选项。

因此脚本把浏览器层的结果分成两类，**都不静默**：

- 截图/DOM 拿不到 → 报告为 **未验证项**（默认严格模式导致退出码 2，`--allow-no-browser` 时降级为警告但照样列出来）；
- `--update-preview` 声称刷新却没真的写文件 → **断言失败、退出码 1**。

> 这条断言本身也踩过一次假绿：早先版本先跑 `dump-dom`，拿到空输出就判定"浏览器不可用"，然后顺手断言"`preview.png` 存在且 > 30KB" —— 查的是**上一次遗留的旧图**。于是 `--update-preview` 一个字节都没写，脚本却打印 ok 并以 0 退出。现在只认"文件 mtime 真的变了"，并补上内容哈希锚点。

**在普通（非管理员权限）终端里**，`node src/check-render.mjs --update-preview` 即可补齐这一层、刷新预览图与 provenance。渲染自检的 Node 层断言（30 项，含均值顶点几何误差 0.004px）不受影响 —— 它们已经证明了产物内联脚本画出的 SVG 结构正确。



## 八、已知限制

1. **数据集是占位数据。** 题目附带的 `DataSet.csv` 在考核文档里（飞书 wiki 需登录），开发时无法读取。`src/data/make-dataset.mjs` 按题目给出的字段格式生成了 50 行占位数据（五个维度刻意用了不同分布形状，便于检验算法）。**拿到官方数据后，只需覆盖 `src/data/DataSet.csv` 再执行 `node src/build.mjs`，代码无需任何改动。**
2. **参考图未能读取**，因此 2.2 节的轴分配是基于题目文字描述做的推断，并已在文档中说明理由。如果官方参考图的轴分配与此不同，改动集中在 `app.js` 的 `valueToRadius` / `ribbonPath` 两处。
3. 密度采用对称铺开（见 2.2 第 3 条），与教科书中单侧折叠的地平线图在形状上不完全一致，属于为适配极坐标布局做的调整。
4. 未做移动端手势交互与数据点级 tooltip（仅 SVG 原生 `<title>` 悬停提示）。
5. **`preview.png` 对应的是本次改动之后的版本，但在这台机器上无法自动复跑**，原因见第七节（管理员权限下浏览器拒绝渲染）。渲染自检的 Node 层断言（含均值顶点 0.004px 几何误差）不受影响。
6. 分带层数固定 3 层、采样点固定 73 个，未做成可配置项 —— 题目数据量小（50 条），这个取值已经够用，加配置只会增加噪声。
